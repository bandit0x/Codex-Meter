# Probe TomatoCloud through the enabled local system proxy

Treat TomatoCloud as connected only when its required desktop and data-plane processes are running, Windows has an enabled loopback system proxy, and a real HTTPS request succeeds through that proxy. Use Google's `generate_204` endpoint as the health probe; read the country of the routed public IP from `api.country.is` as optional metadata so a country-service timeout cannot make an otherwise healthy route look blocked. The health probe allows five seconds for connection/TLS establishment and eight seconds overall. The healthy cadence is five seconds and the blocked cadence is one second after the previous attempt completes.

Do not inspect TomatoCloud private IPC, configuration, logs, memory, or credentials. This is less dependent on undocumented TomatoCloud internals, and it detects the important failure mode where every executable is running but the actual route is blocked. The health probe and country lookup have separate failure semantics: a country lookup failure retains the last known country and never blocks a healthy route.

The UI requires two consecutive blocked health probes before replacing an established healthy state with the red alarm. A first transient failure keeps the last healthy display while the one-second retry cadence continues; startup remains in the checking state until the threshold is reached.
